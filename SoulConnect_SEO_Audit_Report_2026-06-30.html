Sitemap & Indexation Audit

⚠️ CRITICAL: Canonical Tag Defect
Every single page in the sitemap (including /about, /contact, /safety, /crisis-support, /terms, etc.) canonicalizes to the homepage. This means NO inner page will be independently indexed. The sitemap is functionally non-operational.

Sitemap Status

Check Result Impact

Declared in robots.txt ✓ PASS Google will discover it

Redirected URLs in sitemap ✗ /signup, /login → 307 to /maintenance Waste crawl budget
Per-page metadata ✗ All identical <title>, og:* React SPA without SSR

Root Cause: React SPA Without Server-Side Rendering

All routes return the same index.html shell with identical <title>, meta description, and canonical tag. Per-route metadata is supposed to be injected client-side after React mounts, but Googlebot's first crawl sees only the shell.

Consequence: Googlebot reads all 13 URLs as pointing to the same content (the homepage). Google consolidates them into one indexable entity. None of the inner pages are indexed as separate pages.

What Needs to Happen

Implement Server-Side Rendering (SSR) or Static Prerendering

Options:
• Next.js migration (best long-term solution)
• Vite SSR (medium effort, Vite-native)
• Vercel prerendering (quick, built into Vercel)
• Prerender.io (third-party service, works with any SPA)

Each public page must have a unique <title>, <meta description>, and self-referencing canonical before the sitemap provides any indexation benefit.

Critical Issue #2: SPA Renders 72 Characters Without JavaScript

Every public page returns the same HTML shell to crawlers:

<div id="root">
  <!-- Loading spinner only until React mounts -->
</div>
<script src="/assets/vendor-react-*.js"></script>

AI crawlers (except Googlebot) do not execute JavaScript. They see:

  • No headings beyond the <title>
  • No paragraphs or prose
  • No questions or answers
  • No FAQ content (it's in JSON-LD <head> only)

What saves partial credit: The 7 JSON-LD blocks in <head> are visible without JavaScript. Crawlers that parse structured data can extract FAQPage answers (though they're too short — see below).

Critical Errors to Fix

LocalBusiness Telephone Error
"telephone": "+91-support"

This is not a valid E.164 phone number. Schema validators flag this as an error. Either:
• Replace with a real phone number in format +91-XXXXXXXXXX
• Remove the field entirely (preferred if no dedicated support line exists)
Missing Physical Address in LocalBusiness
LocalBusiness requires a streetAddress field for physical locations. If SoulConnect is entirely remote, remove the LocalBusiness schema — it's inappropriate for a digital-only service.
hasMap Points to Homepage
The LocalBusiness hasMap field should point to a Google Maps URL, not https://soulconnect.health/. Either add a correct Google Maps URL or remove the field.
